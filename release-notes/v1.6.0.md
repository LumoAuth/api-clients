## Highlights & New Features

### 1. Sign-in Methods for Your Own Sign-in Form (`OAuth` API)

An application that renders its own sign-in form can now ask which sign-in methods the organization offers. The form can then show the next step after a person types an email address.

- New operation `checkEmailFirst`: `POST /orgs/{orgId}/api/v1/oauth/check-email`. It needs no authentication and signs nobody in.
- Request body: `CheckEmailFirstRequest`:
  - `email` (required): the address that the person typed.
  - `client_id` (required): the client ID of an active application of the organization.
- Response: `CheckEmailFirstResponse` with `exists`, `magic_link_enabled`, `passkey_enabled` and `password_enabled`.
- The answer is the same for every address. `exists` is always `true`, so the endpoint does not reveal which addresses have accounts. Show the same next step to everyone.
- A browser request must come from one of the allowed origins of the application. Other origins get 403 `origin_not_allowed`.
- Errors: 400 `invalid_request` or `invalid_client`; 404 `not_found` (unknown organization); 429 `rate_limited`, with the seconds to wait in `Retry-After`.

```python
import lumoauth_api_client

configuration = lumoauth_api_client.Configuration()

with lumoauth_api_client.ApiClient(configuration) as api_client:
    oauth = lumoauth_api_client.OAuthApi(api_client)
    methods = oauth.check_email_first(
        "acme",
        lumoauth_api_client.CheckEmailFirstRequest(
            email="ada@example.com",
            client_id="my-spa",
        ),
    )
    if methods.magic_link_enabled:
        ...  # Offer "Email me a sign-in link" (requestMagicLink).
    elif methods.password_enabled:
        ...  # Show the password step.
```

### 2. Restore a User That SCIM Deleted (`Admin: Users` API)

When an identity provider removes a user through inbound SCIM, LumoAuth soft-deletes the user. You can now find such users and bring them back.

- New operation `adminUsersRestore`: `POST /orgs/{orgId}/api/v1/admin/users/{userId}/restore`. The response is `AdminUsersRestoreResponse`, with the restored `User` in `data`.
- The account keeps the roles, groups and permissions that it still holds, and its active and blocked state. Its sessions and tokens stay revoked, so the user signs in again.
- An erased user cannot be restored.
- Errors:
  - 403: the user holds privileges that the caller lacks, or the plan has no free administrator seat.
  - 404: no such user in this organization.
  - 409: `user_not_deleted`, `user_erased`, or `address_in_use` when another account uses the address.
- New fields on `User`: `deleted` and `deletedAt`.
- `listUsers` leaves soft-deleted users out. Pass `deleted=true` to list only them.

```python
users = lumoauth_api_client.AdminUsersApi(api_client)
deleted = users.list_users("acme", deleted=True)
for user in deleted.data:
    users.admin_users_restore("acme", user.id)
```

### 3. Filters, Paging and Sorting for Lists

`listUsers` (`GET .../admin/users`) now documents its query parameters, so every client can send them:

- `page` (from 1) and `limit` (1 to 100, default 25).
- `search`: users whose email address, name or username contains this text. The match is case-sensitive, and the server uses the first 100 characters.
- `active`, `blocked`, `emailVerified` and `mfaEnabled`: filters that take `true` or `false`.
- `deleted`: see [Restore a User That SCIM Deleted](#2-restore-a-user-that-scim-deleted-admin-users-api).
- `role` and `group`: only users who hold the role, or belong to the group, with this slug.
- `sortBy` (`email`, `name`, `username`, `createdAt` or `lastLoginAt`) and `sortDir` (`ASC` or `DESC`). Without `sortBy`, the newest users come first.

Two more list operations have new query parameters:

- `adminAgentsList`: `sortBy` (`name`, `agentId`, `status`, `createdAt` or `lastUsedAt`; default `name`) and `sortDir` (default `ASC`).
- `abacPoliciesList`: `action` lists only the policies that name this action, alone or in a comma-separated list. `*` lists the policies that name `*`.

`ListUsersResponse`, `AdminGroupsListResponse` and `AdminMcpServersListResponse` have a new `resourceType` field.

### 4. Email Sender and General Settings Take a Request Body (`Admin: Settings` API)

In 1.5.0, the operations that change these settings had no request body in the specification. The typed clients could not send any values with them.

**Email sender:** `putAdminSettingsEmailUpdate` and `patchAdminSettingsEmailUpdate` take the new `PutAdminSettingsEmailUpdateRequest`.

- The fields are `fromEmail`, `fromName` and `replyToEmail`. `fromEmail` must be a sender that is verified at the mail provider. Send `null` or an empty string to clear `fromName` or `replyToEmail`.
- `PATCH` changes the fields that you send. `PUT` replaces all three, so `fromEmail` is required.
- The organization needs its own mail provider, which you set up in the portal. Without one, LumoAuth sends the mail, and a write is refused with 400.
- The caller needs `settings.manage` and `users.delete`. An access token must come from a sign-in within the last 10 minutes.

**General settings:** `putAdminSettingsGeneralUpdate` and `patchAdminSettingsGeneralUpdate` take the new `PutAdminSettingsGeneralUpdateRequest`.

- The fields are `name` and `locale`.
- `name` is the name of the organization: one line, 1 to 255 characters. `tenantName`, `display_name` and `displayName` are other spellings of the same field.
- `locale` is the default language of the hosted pages: `en`, `es`, `fr`, `de`, `pt_BR`, `it`, `nl`, `ja` or `ar`. A change of `locale` also needs the `branding.edit` permission.
- `timezone` is not a setting, so the server refuses it with 400. Dates are shown in UTC.
- `PUT` and `PATCH` behave the same.

**New model `EmailSenderSettings`:** the email settings now come back as this typed object. It replaces a free-form map in `adminSettingsEmailGet`, in the email update operations and in the `email` part of `adminSettingsAll`.

- `sender`: `provider` while the organization's own mail provider is switched on, else `platform`.
- `provider`: the provider that is set up (`ses`, `sendgrid`, `mailgun`, `resend`, `postmark` or `smtp`), or `null`.
- `enabled`, `fromEmail`, `fromName` and `replyToEmail`.

```python
settings = lumoauth_api_client.AdminSettingsApi(api_client)
settings.patch_admin_settings_email_update(
    "acme",
    lumoauth_api_client.PutAdminSettingsEmailUpdateRequest(
        from_email="no-reply@acme.example",
        from_name="Acme",
    ),
)
```

### 5. Agent Scopes in `<resource>:<action>` Form

An agent's capabilities are OAuth scope values, written as `<resource>:<action>`, such as `invoices:read`. The examples in the specification now use this form.

- **`getMe`:** `GetMeResponse` has three new fields for agents:
  - `scopes`: the scope values that the agent may request for this organization's API, which are its capabilities.
  - `scope`: the scope of the token that the agent presented.
  - `scope_narrowed`: `true` when that scope leaves out one of the agent's capabilities.
- **`ask`:** an agent that writes the action in the dot form (`invoices.read`) gets 400 `invalid_action`. A user's action is still a permission slug, such as `document.read`.
- **`ask`:** `AskResponse` has a new `decided_by` field: `capability`, `pdp` or `deny_override`. For a user caller it is always `pdp`.
- **`issueAgentToken`:** `IssueAgentTokenRequest` has a new `scope` field. With `request_type=refresh`, it narrows the refreshed token. The scopes must be a subset of the refresh grant and of the resource token's scope, or the server answers `invalid_scope`.
- **`attest`:** `AttestResponse.scope` holds the issued scope values: the agent's capabilities, or the subset that it asked for. It is no longer required, because the server leaves it out when it issued no scope.

### 6. Other New Fields

- `IntrospectResponse.act`: the RFC 8693 actor of a delegated access token, with earlier actors in an inner `act`. It is set for JWT and opaque tokens.
- `AuthorizationServerMetadata.resource_indicators_supported`.
- `AbacPolicy.builtIn` and `AbacAttributeDefinition.builtIn`: `true` for a policy or definition that LumoAuth provides to every organization. You can read it, but a change, switch or delete gets 403.
- `PutAdminSettingsBrandingUpdateResponse.rejected`: the keys whose value failed validation and was not saved.
- `AdminSettingsAllResponseDataGeneral`: new `displayName` (the same value as `name`) and `locale`.
- `GetServerChallengeResponse.status` can now be `no_authorization_required`, for an MCP server that checks no token.

## Fixes & Specification Changes

### UserInfo Refuses Client Credentials Tokens

LumoAuth now refuses a token from the client credentials grant at `userinfo` (`GET` and `POST .../oauth/userinfo`) with 401 `invalid_token`, for JWT and opaque tokens. Such a token names no person and no agent.

- `UserinfoResponse.client_id` is removed.
- `UserinfoResponse.identity_type` is set only for agents, and its only value is `agent`.

### MCP Servers That Check No Token

An MCP server that checks no token is a server set to Public, or a stdio server.

- `getProtectedResourceMetadata` answers 404 `not_found` for such a server. It used to answer 400 `not_applicable`, which is no longer documented.
- `getServerChallenge` and `postServerChallenge` answer 200 with `status: "no_authorization_required"`.
- `listServers` and `getServer` (`GET .../mcp/servers` and `.../mcp/servers/{serverId}`) need the `agents.view` permission. The specification used to name `settings.manage`.
- `AdminMcpServersListResponse.meta` is now a `PaginationMeta`, as in the other list responses. Besides `total`, `page` and `limit`, it has `totalPages`, `hasNextPage` and `hasPreviousPage`.

### Dynamic Client Registration

The description of `registerClient` now lists the metadata that LumoAuth refuses with `invalid_client_metadata`:

- `grant_types` other than `authorization_code` and `refresh_token`.
- `response_types` other than `code` and `none`.
- `subject_type` other than `public`.
- `sector_identifier_uri`, `request_uris` and `userinfo_signed_response_alg`.
- An `id_token_signed_response_alg` other than the organization's signing algorithm.
- Every encryption member (`id_token_encrypted_response_*`, `userinfo_encrypted_response_*`, `request_object_encryption_*` and `authorization_encrypted_response_*`).

`RegisterClientResponse` and `RegisteredClientMetadata` (the response of `getClientConfiguration`) no longer have `request_uris`, `sector_identifier_uri`, `subject_type` or `userinfo_signed_response_alg`.

### ABAC Policies

- `AbacPolicy.action` is one action, several actions separated by commas (`read, write`), or `*` for every action. It is at most 100 characters long. Actions compare case-sensitively, and spaces around the commas don't count.
- `abacPoliciesCreate`, `putAbacPoliciesUpdate` and `patchAbacPoliciesUpdate` answer 400 for an invalid `resourceType` or `action`.
- Built-in policies and attribute definitions cannot be deleted (403). See `builtIn` above.

### Fields That Are Gone or Have No Effect

- `timezone` is removed from `AdminSettingsGeneralGetResponseData` and `PutAdminSettingsGeneralUpdateResponseData`. It is not a setting.
- `OAuthScope.isDefault` is removed. `OAuthScope.description` is the text that users see on the consent page next to the scope name.
- `SocialLoginProvider.customClaims` is deprecated and always `null`. The server accepts it on create and update and ignores it. Ask for more profile data with `requestedScopes`.

### ID Path Parameters

The specification now gives most numeric ID path parameters a pattern for a whole number from 1 to 2,147,483,647. These include `webhookId`, `roleId`, `permissionId`, `groupId`, `sessionId`, `tokenId`, `scopeId`, `invId`, `logId`, the `id` of ABAC policies and attribute definitions, and the number in `authenticatorId`.

The PHP client checks the pattern before it sends the request, and throws an `InvalidArgumentException` when the check fails. The pattern has no anchors, so only a value without a digit from 1 to 9, such as `0` or `abc`, fails the check. The other clients don't check it.

### Documented Responses

The specification now lists these answers:

- **Plan limits (403 `plan_limit_reached`):**
  - `createUser`: no free admin seat for a user with admin access (`limit`: `admin_seats`), or a plan with a hard cap of monthly active users that has no free place this month (`limit`: `mau`, with `resets_on`).
  - `adminOrgInvitationsCreate` and `adminOrgInvitationsResend`: the invited address has no account and the cap of monthly active users is reached.
  - `adminOrganizationsCreate`: the plan allows no further customer organization.
  - `adminRolesAddPermissions` and `adminRolesUpdatePermissions`: too few admin seats for the holders that the role would make administrators. `requested` says how many seats the change needs.
- **Recent sign-in:** `setUserPassword`, `setUserPasswordPost` and `deleteUserAuthenticator` need a token from a sign-in within the last 10 minutes (401 `insufficient_user_authentication`). An administrator who holds a second factor also sends `X-MFA-Challenge` with an approved step-up challenge (403 `step_up_required`). Organization API keys are exempt. `adminIdentitiesLegacySamlRelink` needs the same recent sign-in, unless the request sends `"dry_run": true`.
- **Permissions (403):**
  - The organization and tenant updates (`PUT` and `PATCH` `.../admin/organization` and `.../admin/tenant`) need `settings.manage`, and `gdpr.manage` to change the audit log retention.
  - The `auth` and `authentication` settings updates need `settings.manage`, with extra rules for `cimd_allowed_scopes` and social providers.
  - LumoAuth refuses a branding update that sets `custom_css`, `custom_html` or `show_powered_by: false` on a plan that does not include them.
- **Organizations:** `adminOrganizationsCreate` and the organization updates answer 400 for a field that does not fit, and 409 only when the slug is taken. `adminOrgRolesCreate` answers 400 for an invalid name, slug or description, and 409 when the slug exists. `adminOrgInvitationsCreate` answers 429 for too many invitations in the last hour.
- **Roles:** `adminRolesAddPermissions` and `adminRolesUpdatePermissions` answer 400 for an unknown permission, 403 for a permission that the caller does not hold, and 404 for an unknown role. They check every permission before they change anything.
- **Rate limits (429):** the OAuth endpoints (`authorize`, `token`, `par`, `revoke`, `introspect`, `deviceAuthorization`, `backchannelAuthorize`, the device verification page and `registerClient`) now say that `Retry-After` holds the seconds to wait.

### The Permissions That Each Operation Needs

The descriptions of these operations now name the permissions that they need, the same ones as the matching portal page:

- `adminAuditLogsExport`: `audit.export` and `audit.view`.
- `adminEmailTemplatesList`, `adminEmailTemplatesGet` and `adminEmailTemplatesVariables`: `settings.manage` and `users.delete`.
- `getMfaCoverageReport`: `users.view` and `settings.view`.
- `getStreamConfig`: `webhooks.view` and `agents.view`. `verifyStream`: `settings.manage`.
- `adminClientsGetBranding`: `branding.view` and `clients.view`.
- The audit log retention updates: `settings.manage` and `gdpr.manage`.
- `adminSettingsAll`: `settings.view`. The `branding` part comes back only to a caller who also holds `branding.view`.
- The role and group operations (`adminRolesCreate`, `adminRolesAddPermissions`, `adminRolesUpdatePermissions`, `adminRolesRemovePermission`, `adminGroupsCreate`, `adminGroupsAddRole`, `adminGroupsUpdateRoles` and `addUserPermission`): the caller must hold every permission that it grants. A role that opens the admin portal takes an admin seat for each active holder who is not an administrator yet.

### Other Description Changes

- The `authz/check` examples send `{"resource_id": ...}` as context. The check reads `resource_id` and the defined environment attribute slugs.
- `OpenIdConfiguration.acr_values_supported` is the same list for every organization.
- `op_policy_uri` and `op_tos_uri` in the discovery documents come from the Privacy policy URL and Terms of service URL of the login page settings.
- `AdminAnalyticsDashboardResponseDataAudit.eventsLast7Days` counts the audit events of the last 7 days, or of the plan's audit retention period when that is shorter.

## Breaking Changes

No operation was removed. These changes can break code that compiles against 1.5.0:

| Change | Effect in typed clients |
| :--- | :--- |
| `adminSettingsEmailGet`, the email settings updates and `adminSettingsAll`: the email data is now `EmailSenderSettings` instead of a free-form map | Code that reads it as a map must use the typed fields. |
| `AdminMcpServersListResponse.meta`: `AdminMcpServersListResponseMeta` → `PaginationMeta` | The old model is removed. `PaginationMeta` has the same `total`, `page` and `limit`. |
| `UserinfoResponse.client_id` removed; `identity_type` only `agent` | The getter is gone. The Java and C# enums lose their client and unknown values. |
| `AttestResponse.scope` is optional | Go `string` → `*string` (use `GetScope()`), Rust `Option<String>`, TypeScript `scope?: string`, Python `Optional[str]`. |
| Removed fields (see [Fields That Are Gone or Have No Effect](#fields-that-are-gone-or-have-no-effect) and [Dynamic Client Registration](#dynamic-client-registration)) | Their getters, setters and properties are gone. |
| New query parameters on `listUsers`, `adminAgentsList` and `abacPoliciesList`, and a new request body on the four email and general settings updates | See the notes per language. |

Notes per language:

- **Java:** the new parameters are positional. `listUsers` takes 12 more parameters, `adminAgentsList` 2, `abacPoliciesList` 1, and each of the four settings updates 1 (the request body), along with their `WithHttpInfo` and `Async` variants. Pass `null` for each new parameter to keep the 1.5.0 behaviour.
- **C#:** the new parameters are optional, so existing calls compile. Recompile your code. Constructors of changed models have new parameters in the middle:
  - `User` has `deleted` and `deletedAt` before `mfaEnabled`. Positional arguments after `blocked` now go to other parameters: a value for `mfaEnabled` sets `deleted`. Use named arguments.
  - `GetMeResponse`, `AskResponse`, `AbacPolicy`, `AbacAttributeDefinition` and `PutAdminSettingsBrandingUpdateResponse` have new parameters before their last ones. This matters if you build these responses in tests.
- **TypeScript:** the class API takes one request object and is unchanged. If you call the functional API (`AdminUsersApiFp`, `AdminAgentsApiFp`, `AdminAbacApiFp`, `AdminSettingsApiFp` or their factories) with positional arguments, the new parameters come before `options`. Move `options` to the end.
- **Go:** the module path stays `github.com/lumoauth/api-clients/go`, so `go get` picks up the type changes above in a minor version. Check your build before you upgrade. The new parameters are builder methods, so existing calls compile.
- **Python and PHP:** the new parameters are optional, so existing calls work unchanged. A PHP call that passes `$contentType` by position must pass it by name now.
- **Rust (not published):** the new parameters are positional `Option` arguments. Struct literals of changed models must add the new fields or end with `..`.
- **Swift and Ruby (not published):** the new parameters are optional. The removed fields are gone from the models.
- **Older clients:** the Python and Java 1.5.0 clients cannot read `status: "no_authorization_required"` from the MCP challenge operations. They throw on an enum value that they don't know. Upgrade to 1.6.0 if you call these operations for an MCP server that checks no token.
